# Portfolio Content Admin

This repo includes a local MVP admin panel for editing the static portfolio content source:

- Content source: `content/site.yaml`
- Admin service: `services/admin-api/`
- Same-site login route: `/login/`
- Local admin service UI: `http://127.0.0.1:8791/login`
- Direct API path: `/v1/...`
- Same-origin API path for the portfolio site: `/api/v1/...`

The admin panel validates YAML before saving and creates a local backup under `services/admin-api/data/backups/` before each write.

In production, content is stored in MySQL. Local development can still fall back to `content/site.yaml` when MySQL env vars are not set.

## Setup

```bash
cp services/admin-api/.env.example services/admin-api/.env.local
```

Set `PORTFOLIO_ADMIN_EMAIL` and `PORTFOLIO_ADMIN_PASSWORD`. Do not commit `.env.local`.

## Run

```bash
npm run admin:api
```

Open the local admin service directly:

```text
http://127.0.0.1:8791/login
```

The exported portfolio site also includes a static `/login/` page. That page expects the protected admin API to be reachable on the same origin at `/api/v1`.

For production, place the admin API behind a private/VPN/SSO boundary and reverse-proxy only `/api/` to it. Do not expose the API publicly with only a weak token.

Paste the token, load content, edit YAML, validate, then save.

## Validate from CLI

```bash
npm run content:validate
```

## MySQL migrations and seed

The admin/content database is MySQL-backed. The migration runner:

1. creates the `portfolio` database when admin credentials are available,
2. creates/grants the `portfolio_admin` application user,
3. applies SQL migrations from `services/admin-api/migrations/`,
4. seeds the initial `site` document from `content/site.yaml` if the table is empty.

Run manually:

```bash
npm run db:migrate
```

Required env vars:

```text
PORTFOLIO_MYSQL_HOST
PORTFOLIO_MYSQL_PORT
PORTFOLIO_MYSQL_DATABASE
PORTFOLIO_MYSQL_USER
PORTFOLIO_MYSQL_PASSWORD
PORTFOLIO_MYSQL_ADMIN_USER
PORTFOLIO_MYSQL_ADMIN_PASSWORD
```

In Kubernetes, these values come from Vault via ExternalSecret:

```text
kv/k3s-ha00/portfolio/mysql
kv/k3s-ha00/portfolio/admin
```

The Helm chart includes a post-install/post-upgrade Job that runs:

```bash
node /app/services/admin-api/src/migrate-and-seed.js
```

## Publishing

This MVP intentionally does **not** commit, tag, push, or deploy. After saving content locally:

1. Review the diff:
   ```bash
   git diff -- content/site.yaml
   ```
2. Run validation/build:
   ```bash
   npm run content:validate
   npm run build
   ```
3. Commit/tag/deploy explicitly when ready.

This keeps production changes traceable and avoids giving the admin panel deployment credentials.

## Security Notes

- The service binds to `127.0.0.1` by default.
- API endpoints require the configured admin email/password via HTTP Basic auth.
- The backend only reads/writes `content/site.yaml`.
- Save requests are rejected if validation fails.
- Runtime data and backups live under `services/admin-api/data/`, which is ignored by Git.
- Do not expose this service publicly without VPN/SSO or another strong access boundary.

## Same-Service `/login/` Flow

The `/login/` page is generated by Next.js as part of the static site. It renders the same admin interface but uses this API base:

```text
/api/v1
```

A typical same-domain deployment shape is:

```text
https://kousha.dev/login/       -> static admin login page
https://kousha.dev/api/v1       -> protected admin API upstream
```

The static page alone cannot write content; the API must be running behind `/api/v1` for login, validation, and save operations.
